# java-run 工程能力与技术路线

java-run 的产品目标是为 Maven 与 Gradle 的 Java 源码工作区提供可复用的启动入口。当前已具备单目标运行、自动准备、项目配置、交互补选和独立 JVM 启动能力；架构契约见 [架构文档](architecture.md)，贡献与验证流程见 [贡献指南](../CONTRIBUTING.md)。

## 当前能力评估

评估依据当前运行契约、实现边界和验证证据。

| 能力 | 实现依据 | 工程评价与限制 |
| --- | --- | --- |
| 产品与配置 | `RunConfig` 表达构建工具、单目标、构建策略和三类参数；严格校验 `.java-run.json` | 通用启动模型清楚，框架通过正常参数配置；尚无命名运行配置 |
| 构建语义 | Maven 有效模型与依赖解析、Gradle source set 与任务图 | 构建工具保有依赖裁决权；Maven 多模块准备写入本地仓库，Gradle 配置需要执行项目构建逻辑 |
| 模块设计 | CLI、两种构建适配器、核心启动和进程处理按职责组织 | Maven / Gradle 差异集中，统一准备结果可复用；扩展接口应由新增的真实需求驱动 |
| 启动正确性 | 目标类路径隔离、测试作用域开关、class 文件入口扫描、Manifest URL 编码 | 主类和类路径有直接执行验证；自动发现仅支持传统 main，运行依赖于现有 classpath 契约 |
| 进程管理 | 异步执行、结构化退出状态、子环境覆盖、平台专用进程树清理 | 失败能够定位到阶段，退出码保留；Windows 强制终止不能保证应用关闭钩子执行 |
| 验证 | Bun 回归、真实 JDK、Maven / Gradle 夹具、编译后二进制 smoke | 覆盖正常启动、依赖与资源变化、参数、配置、目标隔离和平台边界；夹具结果不代表所有第三方构建插件兼容 |
| 分发 | 固定 Bun、锁文件安装、原生检查与受检 tag 发布工作流 | 已建立发布门禁和校验和；正式版本仍需许可证、版本及产物验收 |

## 验证与支持依据

[Check 工作流](../.github/workflows/check.yaml) 在 Ubuntu、macOS、Windows 上分别使用 JDK 17 和 21，执行锁文件安装、类型检查、回归测试、本机二进制编译以及完整 Maven / Gradle 验收。Gradle 在 CI 固定为 8.14；Maven 使用运行环境中的命令，不应把 CI 的单一安装版本扩大为整个 Maven 版本系列的兼容承诺。

回归围绕以下可观察结果维护：

- 单项目与 app 依赖 lib 的多模块项目能够启动指定目标
- 无关应用不进入目标运行类路径，默认不加载测试输出和测试依赖
- POM、依赖、profile、资源和配置变化影响下一次运行
- 主类发现、Manifest 和实际 Java 启动覆盖特殊路径与 Unicode 标识符
- 应用参数、JVM 参数、构建参数和子环境保留各自边界
- 正常退出、失败、终止和命令缺失产生明确结果，并清理受控进程树
- 静态计划、帮助和版本遵守各自的副作用契约
- Windows 编码、Maven 配置根和批处理调用有对应的原生验证

[Release 工作流](../.github/workflows/release.yaml) 先执行 Check，再构建 Windows x64、Linux x64 / arm64、macOS x64 / arm64 五种产物并生成 SHA-256。交叉编译产物和原生 runner 的验证范围应分别声明；尚未原生运行的体系结构需要保留验收项。

## 技术路线

优先级依据当前支持契约和使用证据安排。每个阶段以可检查的交付条件结束，不预设未经测量的提速比例或缺少项目样本的兼容承诺。

| 优先级 | 目标 | 交付内容 | 完成条件 |
| --- | --- | --- | --- |
| P0 | 发布可依赖的通用版本 | 确定许可证与版本号；整理支持矩阵；验证 tag 产物的版本输出、安装与校验方式 | 发布文档与实际产物一致，源码检查通过，宣称支持的系统与体系结构有对应运行证据 |
| P1 | 扩展真实项目兼容性 | 增加 Wrapper、自定义输出、构建约定和不同 Maven / Gradle 版本的代表项目；明确 toolchain 与应用 JDK 选择 | 新样本可重复验收，失败边界可解释，既有目标隔离与参数契约保持成立 |
| P1 | 改善重复启动体验 | 根据使用反馈评估命名运行配置、可读诊断和配置辅助；保持命令可直接用于脚本 | 有明确的重复操作或诊断需求，交互与非交互都能完成相同运行目标，配置行为有稳定契约 |
| P2 | 降低启动准备成本 | 测量冷准备、温准备、构建工具启动次数和配置成本；据结果优化 Maven 多次调用或 Gradle 元数据读取 | 在固定样本上有可复现收益，依赖与资源变更回归仍通过，不引入失效条件不完整的独立类路径缓存 |
| 按需 | 扩展运行模型 | 分别评估 JPMS、现代 main、原生任务集成及其他构建系统 | 每种模式先有项目样本、明确的配置与退出契约，再确定适配器接口和支持范围 |

许可证和正式版本是发布决策；版本号应表达实际运行契约。正式发布时需要共同核对 README、支持声明、版本输出与安装产物。

## 架构决策原则

TypeScript / Bun 承担 CLI、配置和进程编排，并提供独立可执行文件与跨平台构建能力。

Maven 与 Gradle 适配器保持各自的模型语义，统一的是准备结果和 Java 启动契约。后续扩展不以相似命令行外观代替语义验证，也不将框架专用运行任务默认等同于直接 Java 启动。

命名配置、诊断和性能优化优先服务日常启动。新增能力需要同时说明配置来源、参数作用域、构建副作用、失败方式和验证样本；无法通过现有 `PreparedProject` 表达的运行模式，应先确认新的结果契约再设计接口。
